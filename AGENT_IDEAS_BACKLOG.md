# Идеи для развития агента (backlog)

Ниже список улучшений, которые можно добавить позже, без раздувания архитектуры.

## 1) `GET /v1/system/processes`
- Назначение: быстро показать в боте топ процессов по CPU/RAM.
- Польза: оперативная диагностика “кто грузит сервер”.

## 2) `POST /v1/remnawave/node/health`
- Назначение: единая проверка состояния ноды.
- Что проверяет:
  - `docker compose ps` по стэку ноды;
  - health/status `remnanode` и web-контейнера (`nginx`/`caddy`);
  - хвост логов с фильтром по critical/error.
- Польза: один endpoint вместо нескольких ручных проверок.

## 3) `POST /v1/remnawave/node/recover`
- Назначение: безопасный авто-recovery ноды.
- Сценарий:
  - мягкая попытка восстановления (restart);
  - при необходимости `down/up`;
  - пост-проверка health;
  - rollback/ошибка при неуспехе.
- Польза: восстановление “в одну кнопку” из бота.

## 4) `POST /v1/security/ports/check`
- Назначение: аудит открытых listening-портов.
- Что делает:
  - собирает фактические порты;
  - сравнивает с ожидаемыми (`ssh`, `agent`, `node`);
  - показывает “лишние” и “отсутствующие”.
- Польза: быстро ловить дыры в firewall/конфиге.

## 5) `GET /v1/system/journal` (ограниченный)
- Назначение: читать системные логи с фильтрами.
- Ограничения:
  - allowlist unit’ов (`docker`, `sshd`, `fail2ban`, `ufw`);
  - лимит строк;
  - без произвольного доступа ко всему journal.
- Польза: удобная диагностика в боте, без SSH.

## 6) `POST /v1/backup/remnanode/config`
- Назначение: backup/restore рабочих конфигов ноды.
- Объекты:
  - `docker-compose.yml`;
  - `nginx.conf` или `Caddyfile`;
  - (опционально) dump UFW rules.
- Польза: быстрый откат после неудачных правок.

## 7) Webhook-уведомления из агента (опционально)
- Назначение: push-события в бот вместо постоянного polling.
- События:
  - `job_failed`;
  - `node_down`;
  - `cert_renew_failed`;
  - `recovery_failed`.
- Польза: быстрее реакция и меньше “пустых” опросов.

## 8) Режим `maintenance window`
- Назначение: временно отключать алерты и авто-восстановление.
- Польза: безопасные ручные работы без шумных инцидентов.

## Рекомендуемый порядок реализации
1. `node/health`
2. `node/recover`
3. `ports/check`
4. `system/processes`
5. остальное по приоритету
